Where the time goes in a Spine polling cycle, and what that means for proposals to rewrite Spine around an event loop. In short: Spine's own CPU use is negligible. Cycle time is dominated by a fixed completion wait, a lock around script launches, and database writes.

Method

Spine 1.2.x was profiled on 11 November 2026 in two setups.

  • Loopback: 200 devices with a mix of SNMP, script and Script Server items, a local snmpd, and MariaDB 10.11 on one aarch64 machine.
  • Real network: a 4 vCPU, 8 GB poller on DigitalOcean, polling simulated SNMP device farms at about 2 ms round trip (same region) and about 76 ms (cross-country), with 500 or 2,000 devices of 23 items each.

Every number below comes from those runs. The harness is not published yet, so treat these as one set of measurements, not a benchmark.

Findings

A fixed half-second completion wait

The main thread checks for finished worker threads every 500 ms, so every cycle ends on a half-second step. On loopback, polling every 10 ms instead cut a mixed 200-device cycle from 1.4 to 2.7 s down to 0.5 to 0.64 s. On the real network the saving was smaller: 0.2 to 1.0 s per cycle, about 5 to 15 percent, and one configuration (2,000 devices on the LAN with 16 threads) got 0.67 s slower.

Script launches serialize on one lock

Spine holds a global list mutex while it starts each script, so script launches and closes queue behind one another across all threads. That accounted for 37 percent of Spine's blocked time on loopback.

The database is the bottleneck on a fast network

Writing results to poller_output was 34 percent of blocked time; SNMP itself was under 2 percent on loopback. On the real network the database server used 53 percent of CPU during a cycle and Spine 27 percent. Spine issues about 8 queries per device, and three of them (the poller_item next-step update, the per-host item select and the poller_output insert) are about 20 percent each.

Threads matter only when latency is high

Across the 76 ms link, 2,000 devices took 31.8 s with 16 threads, 9.4 s with 64 and 7.0 s with 100, the maximum. On the 2 ms network, thread count made no difference (5.5 to 6.1 s) because the database was already the limit.

Spine's CPU use is small

On loopback, Spine used 2.8 percent of cycle CPU, about 9 ms. 97 percent went to the PHP Script Server processes loading Cacti at startup.

Two cases where data was dropped without an error

  • With MariaDB's default max_heap_table_size of 16 MB, the in-memory poller_output table filled at 7,840 rows and Spine still exited successfully.
  • An SNMP timeout dropped 12 rows without a failure exit.

Whether Spine logs either case has not been checked yet.

What this means

None of these numbers justify rewriting Spine around an event loop such as libuv. The changes worth proposing are smaller:

  1. Replace the fixed 500 ms poll with a condition variable or semaphore that wakes the main thread when workers finish.
  2. Narrow the lock held during script launch.
  3. Reduce per-device database round trips, which is where a fast network spends its time.

Each needs re-measuring on a real network before any claim, because loopback hides network round-trip time and exaggerated the completion-wait gain about threefold.
