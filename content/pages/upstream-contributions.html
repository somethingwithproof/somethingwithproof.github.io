Changes to Cacti, Spine and the Cacti plugins go upstream as pull requests from a fork. This page walks through one change from a clean branch to an open pull request, including the mistake that most often makes a pull request unmergeable.

Before you start

  • A fork of the target repository, such as cacti or spine.
  • A clone with two remotes: origin for the fork and upstream for the official repository.
  • PHP 8.2 or later for the Cacti 1.2.x line, or PHP 8.3 or later for develop. PHP 8.4 is the recommended runtime for both.

1. Pick the base branch

Fixes for released versions target 1.2.x. New features and larger refactors target develop. If a fix applies to both, open it against 1.2.x first.

2. Branch from upstream, not from the fork

A fork's copy of 1.2.x or develop falls behind silently. Branching from it produces a pull request that appears to revert hundreds of unrelated upstream commits.

git fetch upstream
git switch -c fix/short-description upstream/1.2.x

3. Make one focused change

  • Keep the pull request to one behavior change, with a test where behavior changes.
  • Match the surrounding code's style, even where you would write it differently.
  • Leave unrelated formatting and renames for a separate pull request.

4. Sign off every commit

Commits need a Developer Certificate of Origin sign-off:

git commit -s -m "fix: describe the change"

5. Check the branch against upstream

A local check can pass even when the branch is behind, because it compares against stale refs. Ask GitHub directly before opening the pull request; the result should be 0:

gh api repos/Cacti/cacti/compare/1.2.x...YOUR-USER:cacti:fix/short-description --jq .behind_by

6. Open the pull request

Open it against the upstream repository and base branch you chose. Link the issue it fixes, explain the behavior before and after, and list how you tested it. Report security issues privately instead; see Reporting a vulnerability.
